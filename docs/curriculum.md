# 课程设计与章节范围

本文件保留课程范围和教学设计。24 章首版正文见[阅读目录](index.md)，路径与可读状态以 `content/chapters.json` 为准；[实际验证](../editorial/validation.md)与正文完成分别记录。下面的实验设计不等于全部已经执行。

## 定位与边界

面向已有一门语言基础的读者，以 Windows 桌面应用为中心，学习独立设计、诊断、交付和维护产品所需的机制与取舍。Windows 是操作系统主线；UI 框架是一条可替换的实现路线。

不承诺“学完即达到某公司高级职级”。课程通过交付任务和证据评估能力，不通过读完多少术语评估能力。

如果从零开始覆盖语言、所有 UI 框架、Windows 内部机制、数据库、驱动、逆向和 AI，这会成为一套丛书。面向已有基础的开发者，可以压缩语法与控件教学，减少框架重复；诊断、兼容性和发布部分需要讲得更深。**收紧的是必修路径，不是删掉高级工程所需的责任。**

范围分为三层：

| 层次 | 学什么 | 完成要求 |
| --- | --- | --- |
| 主线 | Windows 运行机制、UI 状态与并发、模块边界、数据、诊断、交付 | 走通 24 章，留下各阶段产物 |
| 框架选学 | WPF、Qt、Electron、WinUI，以及既有系统路线 | 先选一条，再按需要迁移 |
| 专题查阅 | 驱动、图形、音视频、深度逆向、复杂 COM、设备协议等 | 与岗位和项目相关时再深入 |

前置知识见[学习方法](learning-method.md)。框架路线和官方文档入口见[框架学习](frameworks.md)。

## 贯穿案例及约束

“桌面任务工作台”接收一个目录，分析其中的文件，展示进度、结果和历史记录。分析逻辑可以从文件大小统计开始，避免领域算法掩盖工程机制。

依次增加：后台任务与取消、菜单与托盘、原生 DLL、C ABI SDK、SQLite、诊断信息、安装升级和流水线。网络使用可控的测试服务作为扩展，不在入门时依赖真实账号或公网服务。

主线用 C# / .NET / WPF 解释界面，用 C ABI 解释原生边界。独立原生实验采用 C11 实现并提供 C/C++ 头文件，便于观察最小 ABI；不是已经包含完整工作台的 C++ SDK。实际工具链见[实验说明](../examples/README.md)。读者可用 Qt 或 Electron 实现同等任务；框架特有的问题分别说明，不把 WPF 的线程模型、Qt 的对象模型或 Electron 的进程模型画成同一种机制。

每阶段说明上一阶段留下了什么、本阶段增加什么，以及还不能解决什么。

## 一、程序怎样在 Windows 上运行

### 01 从“一个窗口”到“一个可交付的客户端”

- 主问题：界面之外，还有哪些职责必须有人负责？
- 范围：需求与非功能目标、系统上下文、UI/应用逻辑/数据/系统适配边界、单进程与多进程的初步选择。
- 产物：任务工作台的用户流程、责任图、首版验收清单。
- 实验设想：加入“分析十万文件时仍能取消”的需求，找出仅靠界面代码难以承担的职责。

### 02 从源码到一次可重复的运行

- 主问题：为什么“我电脑能跑”不足以说明项目可交付？
- 范围：编译与链接的基本关系、SDK/运行时/工具链、构建配置、x86/x64/ARM64、Debug/Release、依赖锁定、基础断点调试。
- 产物：干净检出后的构建说明、环境记录、最小可运行窗口。
- 实验设想：更换构建配置或目标架构，记录产物和运行条件的变化。DLL 与 LIB 的细节留到第 09 章。

### 03 进程、线程、内存和句柄：程序到底占着什么

- 主问题：为什么创建对象、启动线程和打开文件都需要考虑生命周期？
- 范围：进程地址空间、栈与堆、虚拟内存的必要直觉、线程调度、句柄和内核对象、托管与原生资源的区别、RAII/确定性释放。
- 产物：资源归属表，能说明谁创建、谁使用、谁释放。
- 实验设想：重复执行任务，观察线程数、句柄数和内存趋势；区分增长现象与已证实泄漏。

### 04 窗口为什么会“未响应”

- 主问题：用户的点击如何变成程序行为，阻塞发生在哪一环？
- 范围：HWND、消息队列与消息循环、窗口过程、事件分发、重入、创建与关闭时序。说明各框架如何包装这些机制及其差异。
- 产物：从点击“开始”到任务完成的一条时序图。
- 实验设想：在界面线程制造可控阻塞，观察窗口行为；之后把耗时工作迁走，解释改变了哪条执行路径。

**阶段验收：**另一位读者能从干净目录构建并运行程序；你能画出启动、点击、执行、退出的关系，并解释资源由谁释放。

## 二、界面怎样可靠地响应用户

### 05 菜单栏不是一排按钮：命令、状态和输入

- 主问题：同一个动作由菜单、快捷键或托盘触发时，怎样保持一致？
- 范围：命令与可用状态、菜单栏/上下文菜单/工具栏、焦点与键盘导航、输入法、剪贴板与拖放、DPI/多显示器、基础可访问性与本地化。
- 产物：统一的开始、取消、打开结果命令及交互验收表。
- 实验设想：执行中切换 DPI、仅用键盘操作、从不同入口取消任务；观察状态是否一致。系统托盘的进程生命周期问题另做小节。

### 06 后台任务：异步、取消、超时和关闭

- 主问题：窗口关了，任务和回调还在，谁负责收尾？
- 范围：UI 线程约束、任务调度、进度节流、取消协作、超时与重试、异常传播、退出时序；区别异步和新线程。
- 产物：具有明确状态转换的任务控制器。
- 实验设想：连续开始/取消、关闭窗口时仍有任务、回调晚到；验证不会更新已销毁的界面或重复提交结果。

### 07 业务逻辑为什么不该都住在窗口里

- 主问题：不打开窗口，能否验证任务规则和错误处理？
- 范围：UI 与业务状态分离、MVVM/MVC 的用途和局限、依赖边界、状态机、可替换的系统接口、单元与集成测试分工。
- 产物：可脱离界面执行的应用逻辑与少量关键测试。
- 实验设想：替换文件访问或分析器，注入错误；解释哪些测试仍需真实 Windows 环境。

### 08 怎样学会一套 UI 框架，并迁移到另一套

- 主问题：已经会 WPF/Qt/Electron，换框架时哪些能力保留，哪些必须重学？
- 范围：按窗口生命周期、状态、调度、资源、系统集成和分发比较框架；学习最小官方样例、调试事件路径、建立对照表。
- 产物：一页框架选择说明，以及同一个小功能的迁移记录。
- 实验设想：在第二套框架中只重做“任务列表 + 取消”，不重写整个产品；说明额外进程、运行时和部署条件。

**阶段验收：**任务执行中界面可交互，取消和关闭有确定行为；菜单与快捷键一致；能用证据解释一次框架选择。

## 三、模块怎样交给别人使用

### 09 EXE、DLL、LIB、PDB：构建产物怎样连起来

- 主问题：链接成功了，为什么到客户电脑仍提示找不到模块？
- 范围：PE 的必要结构、导入与导出、静态库与导入库、加载时与运行时动态链接、位数和运行时依赖、加载搜索路径、符号文件。
- 产物：分析模块的产物清单与依赖图；用 Dependencies、dumpbin 和运行时证据交叉判断。
- 实验设想：制造缺少间接依赖、架构不一致、导出不匹配的故障；不把静态依赖树当成完整的运行时加载记录。
- 易错边界：`.lib` 可能是静态库或导入库；`LoadLibrary` 成功也不代表接口调用一定安全。

### 10 API 和 C ABI：怎样把边界写成契约

- 主问题：两边都叫同一个函数，为什么仍会崩溃或读错数据？
- 范围：API 与 ABI、名称修饰、导出方式、调用约定与架构差异、结构体布局、编码、长度与缓冲区、句柄、内存所有权、错误表达、回调线程。
- 产物：一份小型 C 兼容头文件草案，写明版本、生命周期与线程约束。
- 实验设想：用受控的错误布局或生命周期违例演示边界故障，再修复；分别讨论 C# P/Invoke、Qt/C++ 调用和 Electron 原生适配路线。
- 易错边界：`extern "C"` 不会自动解决结构体布局、内存分配器、异常跨边界或所有平台的二进制兼容问题。

### 11 SDK 怎样才能让别人独立接入

- 主问题：交出一个 DLL，为什么还不算交付 SDK？
- 范围：头文件/库/运行时/示例/文档的分工、初始化与关闭、错误码、日志、线程安全、取消、版本查询、源代码兼容与二进制兼容、许可与依赖说明。
- 产物：SDK 包结构、最小接入示例、契约测试与兼容性矩阵。
- 实验设想：在干净工程中接入 SDK，再让旧调用方搭配新库；写清支持的组合和不支持的组合。

### 12 插件放在进程内，还是隔离到进程外

- 主问题：扩展模块崩溃时，是否应该拖垮整个客户端？
- 范围：插件发现、版本协商、装卸生命周期、故障隔离、进程启动与监督、共享内存与消息通信的取舍；认识 COM 的接口、引用计数和线程模型，复杂 COM 留作专题。
- 产物：进程内 DLL 与独立工作进程两种方案的选择依据。
- 实验设想：让分析模块异常退出，比较宿主状态与恢复方式；不把不同进程之间的指针当成可直接共享的对象。

**阶段验收：**不依赖 UI 工程也能接入分析能力；接口契约解释清楚，旧调用方的兼容性有实际验证路径，模块失效时的影响范围明确。

## 四、程序怎样与数据和系统相处

### 13 配置该放文件还是注册表

- 主问题：程序装在哪里，数据就该放在哪里吗？
- 范围：用户与机器配置、已知文件夹、Unicode 路径、文件锁、临时文件与原子替换、注册表键值、32/64 位视图、配置优先级与迁移。
- 产物：配置与数据位置表，区分安装内容、用户数据、缓存和诊断信息。
- 实验设想：标准用户运行、配置损坏、非 ASCII 路径、第二个实例同时访问；记录失败后的行为。

### 14 SQL 与 SQLite：历史记录怎样可靠落盘

- 主问题：任务完成了一半就断电，重新打开后该看到什么？
- 范围：最小关系模型、查询与索引、参数绑定、事务、并发访问、schema 迁移、备份与恢复、WAL 的作用与适用条件。
- 产物：任务历史数据库、升级迁移方案与恢复演练记录。
- 实验设想：中断一次写入、失败一次迁移、模拟并发写入；用实际数据库状态验证结果。
- 易错边界：备份不能假定“复制主数据库文件”总能覆盖完整状态；具体方法需按连接状态和日志模式核实。

### 15 网络与 IPC：消息发出去之后呢

- 主问题：超时、断线和重复请求出现时，谁知道任务到底完成没有？
- 范围：HTTP/Socket 的使用边界、TLS 与代理的基础、命名管道与本地通信、协议帧与版本、超时、取消、幂等、重试、背压、断连后的状态恢复。
- 产物：最小请求协议与失败状态表。
- 实验设想：使用可控服务制造延迟、重复响应和进程退出；比较“重新连接”和“恢复业务状态”的区别。

### 16 标准用户、UAC 和安全边界

- 主问题：为什么不能让整个程序一直以管理员身份运行？
- 范围：用户令牌与提权直觉、ACL、最小权限、凭据与敏感配置、DLL 搜索安全、IPC 调用方与输入校验、Web 内容接入时的边界。
- 产物：权限与信任边界图，逐项说明哪项操作确实需要额外权限。
- 实验设想：用标准用户走完整流程；让不可信输入进入模块边界，验证拒绝或降级行为。

**阶段验收：**数据有明确归属和迁移方案，失败后可恢复；标准用户路径可用；通信失败不会悄悄产生重复任务或模糊状态。

## 五、出问题后怎样找到证据

### 17 客户说“打不开”：从环境与日志开始调查

- 主问题：拿不到客户机器，怎样逐步缩小问题范围？
- 范围：结构化日志、版本与任务关联、事件查看器、Process Explorer、Process Monitor、Dependencies、环境差异与最小复现。
- 产物：经过脱敏的支持包设计与一份调查记录。
- 实验设想：区分进程未启动、依赖加载失败、权限拒绝、后台仍运行但无窗口；每个结论都指向对应证据。

### 18 Minidump、PDB 和调用栈：从崩溃现场继续调查

- 主问题：只有一个 dump 文件，能知道什么，又缺什么？
- 范围：用户态 dump 与采集方式、WER/ProcDump/应用采集方案的适用条件、dump 内容选择、匹配的二进制与符号、WinDbg/Visual Studio、异常上下文和线程栈。
- 产物：自建故障的 dump、匹配的版本产物、分析过程与下一步验证。
- 实验设想：比较有无正确符号、不同 dump 内容时能够回答的问题；分别说明托管异常、原生异常和混合调用的调查入口。
- 易错边界：调用栈不自动等于根因；minidump 不保证包含调查需要的全部内存。采集机制是否适用于所选框架，需要单独验证。

### 19 卡顿、死锁、泄漏和慢启动如何区分

- 主问题：CPU、内存和响应时间各说明了什么？
- 范围：等待链与锁、线程栈、句柄泄漏、托管/原生内存、采样与追踪、ETW/WPR/WPA 的调查入口、性能基线与回归。
- 产物：一个有基线、有证据、有对照的性能或卡死调查。
- 实验设想：分别注入 UI 阻塞、锁等待和资源未释放；先分类，再选工具，最后验证修复后的变化。

### 20 看不到源码时：二进制检查与逆向辅助维护

- 主问题：面对旧 DLL 或第三方模块，哪些信息仍可直接验证？
- 范围：PE 头、导入导出、字符串、符号与反汇编、静态与动态观察的区别；IDA/Ghidra/x64dbg 的学习入口，托管程序集的单独分析路线。
- 产物：对自编测试模块的一份接口与行为调查，标明已观察事实、推断及待验证项。
- 实验设想：对照有源码与无源码时的调查结果；避免用“能看到某个 API 名称”直接推断整段运行行为。
- 范围约束：这里只覆盖维护和诊断需要的基本能力；完整汇编、漏洞利用、驱动和深度逆向不放入主线。

**阶段验收：**对三类故障给出可复核调查：打不开、崩溃、卡住。报告说明证据支持什么、还缺什么，不以工具截图代替因果分析。

## 六、怎样把版本交到用户手里

### 21 安装和卸载：产品怎样进入、离开用户电脑

- 主问题：安装不仅是复制 EXE，卸载时又应该删掉什么？
- 范围：按用户/按机器安装、安装路径与数据路径、运行时依赖、快捷方式、卸载登记、文件/协议关联、安装日志、重启与占用文件；比较 MSI/MSIX 与 EXE 安装器路线。
- 产物：安装清单、卸载清单、数据保留说明与干净环境安装记录。
- 实验设想：安装失败、重复安装、文件占用、标准用户安装和卸载后重装；验证注册表与用户数据处理符合设计。
- 工具位置：WiX、Inno Setup、NSIS 和框架打包工具按方案选学，不要求每套都做完整项目。

### 22 CI：从源码到可追溯的安装包

- 主问题：这个安装包由哪份代码、哪套工具链产生？
- 范围：Git/评审的必要流程、脚本化构建、依赖恢复与缓存、Windows runner、测试分层、安装冒烟、版本号、PDB 与二进制归档、签名与凭据边界、第三方依赖与许可清单。
- 产物：流水线设计、制品清单、版本与符号映射；初稿阶段不预设已有可运行 workflow。
- 实验设想：在干净 runner 中构建并在独立环境安装，验证产物可追溯；认识“能重新构建”和“字节级可复现”的区别。
- 工具位置：先用 GitHub Actions 讲清机制，再映射到 Jenkins 等系统；不做平台语法大全。

### 23 升级与兼容：新版本怎样不伤害旧用户

- 主问题：程序能回退，数据一定也能回退吗？
- 范围：更新包与来源校验、签名、应用和 SDK 版本、配置/数据库迁移、灰度与渠道、失败恢复、回滚与前向修复、兼容性矩阵和发布说明。
- 产物：从旧版本升级的演练记录，以及失败时的恢复方案。
- 实验设想：升级中断、迁移失败、离线、磁盘不足和旧 SDK 调用方；明确不支持回退的条件及数据保护办法。

### 24 AI 时代怎样负责一次工程改动

- 主问题：代码能生成之后，工程师仍然需要做哪些判断？
- 范围：把需求变成可验证约束、提供最小上下文、分解改动、审查系统调用/线程/生命周期/ABI、验证文档与生成代码、诊断信息最小化、依赖和发布变更审核。
- 产物：一次 AI 参与的需求变更记录，包含需求、改动、被拒绝的错误建议、测试与发布风险。
- 实验设想：让 AI 协助迁移 SDK 调用或修复已设计的故障，用独立证据检查结果；不把“AI 说测试通过”当作测试结果。
- 范围约束：在产品中接入模型、流式交互和工具执行属于另一条专题；“用 AI 开发客户端”和“开发 AI 客户端”分别说明。

**阶段验收：**另一台干净环境能够安装并运行候选版本；能从一个崩溃文件找到匹配符号和源码版本；完成一次旧版本升级与失败恢复演练；AI 参与的关键改动能够由维护者解释和复核。

## 综合验收：交付一次需求变化

在原有版本上加入“后台批量分析并允许中途取消”，或“更换分析 DLL 且保留旧 SDK 调用方”。提交设计取舍、实现、故障注入结果、SDK 兼容性记录、安装升级产物和一次故障复盘。

评估重点：

1. 能否确定责任边界，说明为什么选这个方案以及放弃了什么。
2. 能否在取消、退出、异常和迁移失败后保持状态一致。
3. 能否用日志、dump、追踪或复现支持结论。
4. 能否让另一个人独立构建、接入 SDK、安装和调查问题。
5. 能否对 AI 和人工生成的代码承担同样的验证责任。
