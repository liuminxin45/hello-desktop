# 毕业项目：对一次需求变化负责

前面的独立实验让局部机制可观察。毕业项目把它们放回实际产品责任中：从设计到实现、诊断和交付，完成一次有约束的变化。

不需要把所有框架同时用上。选 WPF、Qt、Electron 或其他明确路线，并说明适用条件。真实产品可以比案例简单，但失败语义与验证不能省略。

## 选择一个变化

**方案 A：让已有目录分析界面支持后台任务、取消和历史。** 保留一轮任务规则，处理晚到进度、窗口关闭、读取失败和历史保存失败。

**方案 B：替换分析 DLL，并继续支持旧 SDK 调用方。** 保留旧二进制，验证导出、ABI、行为和部署依赖；不支持的组合必须能被清楚拒绝。

**方案 C：把不可靠分析器移到工作进程。** 设计握手、请求身份、取消、退出与恢复；模拟接受请求后退出，说明是否允许重试以及如何避免重复副作用。

先写用户行为和验收表，再决定是否需要某种设计模式或中间件。

## 六份必须能交给别人的材料

1. **设计说明。** 责任图、时序、状态主人、资源归属、信任边界，至少一个被放弃方案及理由。
2. **源码与构建。** 干净目录可构建，工具链与依赖条件明确，不依赖个人绝对路径。
3. **验证材料。** 正常、取消、重复操作、关闭、权限或通信失败，以及结果不确定时的表达。
4. **接口材料。** 输入输出、所有权、线程、错误、版本与所支持兼容组合。没有公开 SDK，也要说明内部边界。
5. **交付材料。** 安装/卸载范围，旧版升级，数据迁移失败恢复，二进制与符号、源码提交的对应。
6. **故障复盘。** 现象、证据、假设、反证、修复及对照。不以工具截图代替解释。

AI 可协助任一部分；记录重要建议为何接受或拒绝，以及由什么实际结果支持。

## 怎样判断是否通过

| 能力 | 最低证据 | 未通过的典型表现 |
| --- | --- | --- |
| 解释系统 | 能追踪一次操作中的控制、状态与资源 | 只会描述类名，解释不了取消与退出 |
| 独立接入 | 他人按文档构建或调用 | 必须由作者现场修环境和补文件 |
| 处理失败 | 注入故障后状态仍可解释 | 把错误吞掉，结果显示成功 |
| 调查问题 | 证据与结论对应，有后续验证 | 看到系统栈帧就断言系统 bug |
| 维护兼容 | 支持矩阵有实际组合验证 | 版本号没改就认为兼容 |
| 交付恢复 | 安装升级失败有可操作路径 | 删除旧版后才发现新版无法运行 |

没有执行的部分写为未验证，不把阅读或纸面方案当成完整毕业交付。单次完成也不等于公司职级认证；下一步是在陌生需求和真实环境中重复应用这些判断。
