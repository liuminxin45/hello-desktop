# 23 升级与兼容：新版本怎样不伤害旧用户

新版本已经通过正常运行检查，升级后却读不了旧配置。用户回装旧 EXE，数据库又提示格式不支持。应用文件、配置、数据库和 SDK 是几条相关但不同的版本线。

本章把升级看成状态迁移，而不是覆盖文件。

## 列出需要一起演进的对象

| 对象 | 要问的问题 |
| --- | --- |
| 程序与 DLL | 能否一起替换，是否存在新旧混装窗口？ |
| 配置 | 新版能读哪些旧格式，迁移失败是否保留原件？ |
| 数据库 | schema 如何推进，旧程序还能否读取？ |
| SDK 调用方 | 已编译旧调用方能否直接使用新库？ |
| 外部协议 | 对端升级顺序不同，是否还能协商？ |

不要只用一个产品版本号代替所有兼容判断。一个版本可能新增界面而不改 ABI，也可能界面变化很小却引入不可逆数据迁移。

## 更新可以拆成准备与提交

先下载到独立暂存位置，校验来源、完整性和目标条件，再停止或协调运行中的工作，按选定安装机制提交新版本。校验失败不应破坏当前可用版本。

更新元数据同样需要信任保护，不能只验证从同一个未可信来源下载的“文件 + 哈希”。具体签名与更新机制依框架、安装模型和分发渠道而定，不自创一个没有验证的安全协议。

磁盘不足、离线、文件占用、意外重启和用户取消都有各自路径。任何一步都要能判断当前是旧版可运行、新版待完成，还是需要恢复的中间态。

## 程序回退与数据回退分别承诺

把程序目录换回旧版，无法撤销已经执行的数据迁移。可以选择：

- 迁移前备份，并在受支持条件下恢复，但要处理迁移后新增的数据。
- 让一段版本窗口都能读取同一格式，降低回退风险。
- 不支持某些降级，明确阻止旧版打开，并提供前向修复或导出。

没有一种策略免费。兼容格式可能限制新功能，恢复备份可能丢失之后写入，前向修复需要有可识别状态与修复能力。

迁移脚本需要版本判断、事务与可重复执行策略。失败后再次启动，不能把一半完成的步骤误认成完整版本。

## 发布范围也是控制变量

灰度和渠道让影响范围逐步扩大，但前提是版本能识别渠道、诊断能关联构建、停止扩大后有可用应对方案。它们不替代本地测试，也不意味着可以把明显错误交给用户发现。

每次发布说明应讲行为变化、兼容范围、数据迁移和已知限制，而不是只列提交标题。支持人员需要知道旧版本问题是否仍可复现，以及哪个包对应哪些符号。

## 动手：演练一次失败升级

为工作台设计 v1 与 v2：v2 给历史增加一个字段，但仍要读取旧记录。写下迁移前置、提交点、失败标识和恢复步骤。

在可丢弃数据中故意让迁移事务失败，验证 schema 与版本没有出现半完成状态。SQLite 实验覆盖了这个局部；真实安装器替换、断电恢复、签名与渠道没有被它验证。

再设想 v2 已记录一批新数据，此时要求回退 v1。选择一个明确策略，说明哪些数据可能受影响，以及如何在操作前让用户知情。

## 检查理解

**为什么“先备份就能安全回滚”不够？** 备份可能不一致或恢复失败，迁移后新增数据也未必在旧备份中。还要实际验证恢复和可接受的数据损失范围。

**两个 DLL 分别可用，为什么混装仍会失败？** 它们之间可能共享 ABI、依赖或协议要求。版本组合也属于兼容矩阵，而非只测试每个文件。
