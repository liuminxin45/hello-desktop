# 11 SDK 怎样才能让别人独立接入

一个导出函数已经可以调用。另一个团队却仍不断追问：用哪个架构？错误码是什么意思？需要管理员吗？升级 DLL 要不要重编译？这些问题说明交付对象不仅是实现文件。

SDK 是一份可使用、可维护的集成契约。本章将代码、文档、运行条件和兼容性安排到同一份交付中。

## 站在接收者的空工程里

先设想接收者没有你的源码、IDE 配置和聊天记录。一个小型原生 SDK 包可以这样组织，这是结构示意：

```text
include/       公共头文件
lib/win-x64/   导入库（如果支持隐式链接）
bin/win-x64/   DLL 和随包运行依赖
samples/       最小调用方与构建说明
docs/          API 契约、错误、线程与升级说明
licenses/      本包及第三方材料的许可与归属
```

符号可以按支持流程单独归档，不一定全部公开。包内哪些材料存在、哪些平台支持，都必须与实际产物一致。CMake 生成了导入库，不代表所有接收者都必须使用它；显式加载路线可以不依赖导入库。

本书只附小型 C ABI 实验，不声称已经提供完整分析 SDK。目录工作、异步任务与回调仍要按产品需求设计。

## 文档补齐头文件表达不了的内容

为每个入口说明输入、输出、错误、所有权、线程和结束条件。对于异步分析，最容易遗漏的是：

1. 初始化能否重复，失败后需要释放什么。
2. 任务标识是否在库重启后仍有效。
3. 取消函数返回时，工作是否已经停止。
4. 回调是否允许再次调用 SDK，何时保证不再回调。
5. 关闭能否与进行中的调用并发，最多等待多久。

如果无法清晰回答，就先收紧能力，例如首版只支持同步调用，由应用层调度。这减少契约面积，也让错误更容易重现。

## 两种兼容性分别验证

源代码兼容表示旧调用方源码能否用新头文件和库重新构建；二进制兼容表示已经编译的旧调用方能否直接使用新库。API 名称没变，也可能因为结构体、调用约定或行为改变而破坏后者。

| 调用方 | 库 | 需要验证什么 |
| --- | --- | --- |
| 旧二进制 | 新库 | 原导出与旧参数布局仍可用，结果语义未被破坏 |
| 旧源码重编译 | 新头与新库 | 编译、链接和行为仍符合旧用途 |
| 新调用方 | 旧库 | 能否检测能力不足并明确拒绝，而非调用缺失导出 |

版本号是识别工具，不会自行阻止错误组合。调用方先查 ABI 主版本或能力，再决定是否继续；包和日志还应保留精确产品版本与构建标识。

新增函数通常比改变旧函数参数更容易维持旧二进制，但仍需考虑导出、共享全局状态和依赖变更。无法兼容时就明确发布新主版本，并提供迁移说明。

## 最小样例是接入路径，不是内部演示

样例应只依赖公开包，在干净工程里完成加载、版本检查、一次调用、错误处理与释放。不要引用内部项目路径，或省略只有作者机器才有的依赖。

契约检查至少包含正常参数、空输入、可识别的无效参数、重复调用和版本检查。跨线程、关闭竞态及长期资源稳定性只在契约承诺相关能力后加入，不用与公开行为无关的实现细节凑测试数量。

## 动手：把包交给另一个目录

从原生实验的公共头文件和产物建立一个临时包。只依据 README 写最小接入程序，故意不引用原工程。列出所有不得不询问作者的问题，并把答案写回契约。

再保存一份旧调用方二进制，修改库增加一个新入口，重新执行旧调用方。这个练习只验证你实际使用的架构和组合，不代表所有编译器通用兼容。

## 检查理解

**新增参数给默认值，为什么仍可能破坏旧二进制？** 默认值通常在调用方编译时处理，已经生成的调用代码并不会自动采用新参数布局。需要保留旧入口或设计版本化入口。

**SDK 文档为什么要写退出顺序？** 因为调用方必须知道何时可以释放缓冲区、销毁窗口和卸载库。异步工作与回调不清楚，正常调用也可能在退出阶段崩溃。
