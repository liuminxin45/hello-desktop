# 10 API 和 C ABI：怎样把边界写成契约

现在 DLL 能加载，下一步是调用。假如 C++ 一侧返回一个 `std::string`，C# 一侧把它理解为字符指针，函数名即使相同，数据布局仍完全不匹配。

API 描述调用者看到的功能与行为；ABI 约束二进制层如何传参、返回、布局和解析符号。能编译不代表两侧的二进制契约一致。

## 从一个小接口开始

本书的[原生实验](../../examples/native/workbench.h)只对字节求和，不把目录遍历也藏进去。这样输出可以人工推算：`1 + 2 + 255 = 258`。核心声明如下，平台导出宏见完整头文件：

```c
uint32_t wb_abi_version(void);
int32_t wb_sum_bytes(const uint8_t* data, uint32_t length, uint64_t* total);
```

契约要比声明多写一步：

- 返回 `0` 表示成功，`1` 表示参数无效；失败时不承诺输出值。
- `length == 0` 时允许 `data == NULL`，总和为零；非零长度要求可读的有效缓冲区。
- `total` 必须指向可写的 `uint64_t`，内存由调用方持有。
- 同步调用，函数不保留指针，不发起回调，不跨边界抛出异常。
- 实验定义 ABI 主版本为 `1`，先验证 Windows x64；不是跨平台二进制通用格式。

长度用字节计数，不把字符个数与字节数混用。固定宽度整数有助于匹配，但不能验证调用者传入的任意指针是否合法；检查非空不等于保证整个缓冲区可访问。

## extern C 解决的只是其中一部分

C++ 头文件可用 `extern "C"` 表达 C 语言链接，减少 C++ 名称修饰带来的差异。但目标架构和调用约定仍影响导出与调用方式，尤其是 x86。`__cdecl` 等声明需要两边一致；不能把某个 x64 实验推导成所有架构保证。

结构体还涉及字段宽度、对齐和填充。接口需要结构体时，常用显式大小和版本字段支持演进，并在双方检查 `sizeof`/偏移。不要一遇到错位就给所有结构体加 `pack(1)`；那是在改变契约，还可能带来未对齐访问和性能问题。

跨语言字符串必须约定编码、终止方式、长度单位及缓冲区所有权。Windows 宽字符 API 常用 UTF-16，C ABI 也可以明确采用 UTF-8，但 `char*` 本身不说明编码。

## 谁分配，谁提供释放路径

实验让调用方提供输出空间，避免跨分配器释放。复杂对象可以使用不透明句柄：创建函数返回句柄，所有操作通过它进行，最后交还同一库的销毁函数。

不透明句柄并不自动线程安全。还要说明能否并发调用、销毁是否等待后台任务、回调会在哪个线程发生、取消后是否仍可能回调。否则接口看起来“纯 C”，生命周期仍然危险。

C++ 实现需要把异常转换成错误表达，不能让异常越过不支持它的调用边界。跨 CRT、编译器或语言的容器也不应作为默认稳定契约。

## C# 调用如何检查

托管实验用 `NativeLibrary.Load`、导出查找和带 `CallingConvention.Cdecl` 的委托调用同一接口。输出映射为 `ulong`，长度为 `uint`，返回值为 `int`。完整代码在[原生适配器](../../examples/managed/Workbench.Cli/NativeDemo.cs)。

稳定静态绑定还可以采用 `LibraryImport` 或适用的 `DllImport`；要核对 marshalling、字符和句柄设置。不要因为“C# 能找到函数”就跳过类型与生命周期检查。

## 动手：改变一项契约

先验证三字节结果、空输入和无效参数。然后只做纸面修改：把原生输出从 `uint64_t*` 改成 `uint32_t*`，但调用方仍使用 64 位输出，会出现哪些可观察或潜伏的问题？哪些测试输入很可能看不出来？

不要在正常工作进程随意执行无效指针实验；理解契约可以先从可控错误参数和独立测试进程开始。

## 检查理解

**为什么小数值通过测试，仍不能证明类型匹配？** 较小数据可能没有触发高位、符号、溢出或布局差异。必须先核对声明，再选择能触及边界的输入。

**C ABI 是否保证多年兼容？** 不保证。它减少部分语言耦合，但兼容还依赖导出、布局、架构、行为和生命周期。需要明确版本策略和真实调用方验证。
