# 05 菜单栏不是一排按钮：命令、状态和输入

窗口能响应事件后，我们给工作台加上“开始分析”“取消”“打开结果”菜单，再为开始增加快捷键。很快发现：按钮已经禁用，快捷键却仍然启动了第二个任务。

问题在于各入口各自判断状态。本章把“入口”与“动作是否允许执行”分开。

## 一个动作，多种入口

菜单项、工具栏按钮、快捷键和托盘菜单是入口；开始分析是命令。命令需要回答两件事：当前是否可执行，执行时做什么。最终检查应位于应用逻辑里，因为 UI 的禁用状态可能尚未刷新，也不能约束 SDK 调用方。

| 当前状态 | 开始 | 取消 | 打开结果 |
| --- | --- | --- | --- |
| Idle | 目录有效时允许 | 不允许 | 有历史结果时允许 |
| Running | 不允许 | 允许 | 可打开旧结果 |
| Cancelling | 不允许 | 不重复请求 | 可打开旧结果 |
| Succeeded / Failed / Cancelled | 允许新任务 | 不允许 | 依实际结果决定 |

不要让菜单读取一套布尔量、快捷键读取另一套。所有入口调用同一应用命令，状态再投影到各个控件。`CanExecute` 或等价机制改善交互，但不代替执行前校验。

WPF 中可把菜单与快捷键映射到同一 `ICommand`；Qt 可让菜单、工具栏共享 `QAction`；Electron 可让菜单调用明确的应用用例，再把状态同步给 renderer。不同机制的相似点是复用动作与状态，而非控件实现完全一样。

## 输入不只有鼠标

焦点决定键盘输入落在哪里。窗口打开后应有合理的初始焦点，Tab 顺序应匹配视觉顺序，命令不能无条件抢走文本框中的编辑快捷键。

中文输入法的组合输入不等于每次按键都已经形成完整文字。不要在每个按键上直接提交搜索、清空输入或启动任务。应区分文字变化、确认操作与组合状态。剪贴板和拖放内容也需要验证类型、数量、路径和大小，不能假定来自可信文件选择器。

可访问性要求动作有可理解的名称，状态不能只用红绿颜色表示。取消失败时，要给出文字和可继续操作的路径，而不仅闪一下图标。辅助技术能否感知，还需要真实 UI 验证。

## DPI 改变的是尺寸解释

WPF 使用设备无关单位，通常以 1/96 英寸为参考。系统缩放、显示器差异和应用 DPI 感知方式会影响最终像素映射。文本、图标、命中区域与坐标转换需要共同检查，不能只把窗口截图放大。

先用布局容器表达伸缩关系，避免把每个控件锁死在绝对坐标。文本本地化后可能变长，系统字体和用户缩放也会变化。自绘标题栏虽然灵活，却增加了拖动、缩放、系统菜单、键盘和辅助功能责任；首版优先使用标准窗口行为。

## 托盘改变了退出语义

“关闭到托盘”意味着关闭动作只隐藏窗口，进程继续持有任务和资源。“退出”则需要停止接收新任务、取消运行、释放资源并结束进程。必须让用户看得见这一区别，也必须防止隐藏后再无入口恢复窗口。

本案例首版采用关闭即请求退出；托盘作为练习增加。不要仅为了展示一个通知区图标，就偷偷改变生命周期契约。

## 动手：做一张交互验收表

在自己的界面练习中让菜单、按钮和快捷键共用命令。分别在 Idle、Running、Cancelling 状态触发它们，记录真正进入应用逻辑的次数。

再仅用键盘完成选择、开始、取消和退出；改变窗口大小与系统缩放；用含中文与空格的路径。人工记录实际行为，不把“控件默认支持”当成已验收。

验收材料包括命令状态表、键盘路径以及发现的问题。功能可用、视觉清晰和辅助技术可用是不同检查项。

## 检查理解

**禁用开始按钮后，还需要在应用逻辑拒绝重复任务吗？** 需要。快捷键、菜单、代码调用和状态同步延迟都可能绕过按钮。业务不变量必须由真正拥有状态的组件保护。

**为什么不默认自绘整套窗口装饰？** 标准装饰已经承担大量系统交互责任。若品牌或交互收益不足以覆盖补齐和验证成本，保留系统行为更容易交付。
