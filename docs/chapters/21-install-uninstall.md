# 21 安装和卸载：产品怎样进入、离开用户电脑

工作台在构建目录可以运行，还不代表它已经成为可交付产品。安装需要建立运行条件和入口，升级要处理旧状态，卸载要清理产品拥有的内容，同时尊重用户数据。

## 安装清单是一份所有权清单

先列出文件、快捷方式、注册表、关联、服务和运行时依赖。对每一项回答谁创建、由谁升级、何时移除、失败如何处理。

| 项目 | 案例中的选择 |
| --- | --- |
| 应用文件 | 放在受控安装目录，不混放任务历史 |
| 快捷方式 | 指向明确入口，工作目录不承担配置定位职责 |
| 用户数据 | 位于用户位置，默认不因覆盖安装而丢失 |
| 卸载入口 | 随所选安装技术正确登记 |
| 文件/协议关联 | 只在产品确实需要时增加，按系统规则处理 |
| 签名与依赖 | 对应当前版本，并进入产物清单 |

按用户安装和按机器安装影响路径、权限、注册范围与多人共享。不能让安装器提权后，误把管理员账号的数据目录当作未来所有用户的数据位置。

## MSI、MSIX、EXE 不是同一维度

MSI 基于 Windows Installer 的安装模型与数据库，有组件、产品和升级等规则。MSIX 提供包身份与相应部署模型，但应用能力和分发方式需要符合其条件。EXE 是可执行载体，可以是引导程序、MSI 包装或脚本安装器，不能仅凭后缀判断能力。

WiX 用于构建 Windows Installer 等相关交付；Inno Setup、NSIS 常用于脚本化安装。框架打包工具也可能包装这些技术。选型看企业部署、标准用户、升级、系统集成和维护条件，不要求每个人掌握所有安装器语法。

教学级安装器片段如下，不是可直接发布的完整脚本：

```ini
[Setup]
AppName=Teaching Workbench
AppVersion=0.1.0
DefaultDirName={localappdata}\Programs\TeachingWorkbench
PrivilegesRequired=lowest

[Files]
Source: "publish\*"; DestDir: "{app}"; Flags: recursesubdirs
```

这表达用户范围安装，但仍缺包身份策略、入口、卸载数据选择、签名和升级验证。`publish` 内也必须是正确的运行产物，不是随手复制的 `bin` 目录。

## 安装过程会在中途失败

空间不足、目标文件占用、依赖缺失、权限不足和用户取消都需要路径。先准备新内容，验证条件，再按所选安装模型提交；不要靠“先删旧目录，再尝试复制”实现升级。

不同技术有不同的回滚保证。自定义脚本造成的外部改动，未必自动进入安装事务。服务、驱动或额外注册操作越多，需要验证的失败分支越多。

文件被进程使用时，明确选择提示关闭、延后替换或要求重启。强行结束用户任务会影响未保存数据，不能作为无提示的默认策略。

## 卸载不该猜数据归属

删除产品安装的文件和入口，处理自己的注册项，保留或明确询问用户数据策略。禁止对共享位置做宽泛递归删除。若设置“清理全部数据”，应展示具体应用范围，不把整个用户文档目录视为产品所有物。

共享运行时也可能被其他产品使用，不能因为自己依赖它就卸掉全机共享副本。缓存、日志、历史和用户导出分别说明。

## 动手：用矩阵验证生命周期

在可恢复的干净环境中演练：首次安装、重复安装、旧版升级、文件占用、安装中取消、卸载后重装。分别检查入口、文件版本、依赖、注册范围和数据。

本书当前提供安装设计与示意，不分发已签名安装器；本仓库 CI 的实验压缩包也不是正式产品安装包。安装、UAC 和卸载路径需要按所选工具实际验证。

## 检查理解

**复制 EXE 到另一个目录，为什么不等于安装测试？** 运行时、入口、权限、注册、升级和卸载都可能尚未涉及。复制运行只验证其中一部分。

**卸载后保留历史一定是不干净吗？** 不是。历史属于用户数据，可以按明确策略保留。关键是可解释、符合产品约定，并提供适当的清理方式。
