# 07 业务逻辑为什么不该都住在窗口里

取消逻辑写进窗口后，测试必须先创建窗口、填输入、触发事件，再等一个很难稳定复现的时机。问题并不在“缺一个更强的 UI 测试工具”，而在规则没有独立入口。

本章把展示、用例与基础能力分开，并确定每类验证应该在哪里发生。

## 状态只能有明确的主人

扫描器负责扫描，不决定开始按钮是否可点。任务控制器负责一轮执行的状态与身份。ViewModel 将控制器状态转成界面可绑定的数据；View 处理布局、焦点和展示。

MVVM 的价值在于减小规则与控件的耦合，而不在于每个界面都必须有大量抽象层。MVC、MVP 或较简单的呈现模型也能解决类似问题。先说明谁拥有状态，再选择组织方式。

避免两份可独立修改的“真相”：窗口有 `isBusy`，控制器有 `isRunning`，数据库又有第三个状态，三者可能因异常而分离。可以由控制器发布只读快照，界面根据快照计算按钮和提示；数据库保存的是历史与恢复状态，不直接决定当前线程是否还在运行。

## 让接口表达用例，而非暴露控件

```csharp
// 教学接口：真实实现见独立实验，UI 调度由调用方负责。
public interface IScanner
{
    ScanResult Scan(string directory, CancellationToken cancellationToken);
}

public sealed record ScanResult(long FileCount, long TotalBytes);
```

扫描器不接收 `TextBlock` 或窗口句柄。输入是目录与取消意图，输出是结果；失败约定由接口说明补充。这样命令行、WPF 和测试都能调用。

当需要验证慢执行、错误或晚到消息时，可以用可控制的替身实现接口。测试主动释放一个门闩再让任务结束，比“睡 100 毫秒猜它已经启动”更稳定。

但不要给每个简单类型都制造接口。只有外部效应、需要替换的实现或重要用例边界，才值得承担抽象成本。

## 分层验证，各有盲区

| 验证层次 | 适合发现什么 | 不能代替什么 |
| --- | --- | --- |
| 状态与纯规则测试 | 重复启动、非法状态转换、旧消息过滤 | Windows 真实调度 |
| 文件系统集成检查 | 路径、枚举、资源释放、实际异常 | 客户机器所有权限组合 |
| 原生契约检查 | 参数与输出、导出、架构、版本 | 完整 UI 或安装升级 |
| UI 检查 | 焦点、键盘、状态显示、关闭 | 内部所有失败分支 |
| 安装升级演练 | 干净环境、依赖和数据迁移 | 业务算法全面正确 |

测试不是越多越好，而是对重要不变量提供直接证据。本案例的独立检查关注：空目录返回零、统计正确、取消被观察、资源可释放、路径错误不伪装成功。

目录树正在变化时，“文件数等于某个固定常量”可能不是稳定契约。测试输入必须受控，预期必须与应用真正承诺的行为一致。

## 错误在边界上翻译

扫描器的访问错误保留诊断上下文；控制器把它归类为本轮失败；ViewModel 提供适合显示的提示。不能一路捕获后只返回零，因为零同时代表合法的空目录。

也不要把所有底层异常文本原封不动展示给用户。可以展示简短原因、任务标识和重试/选择其他目录的选项，把详细上下文写进支持日志。第 17 章再安排证据格式。

## 动手：不启动窗口也能测试

读[实验中的扫描器](../../examples/managed/Workbench.Core/DirectoryScanner.cs)和[检查程序](../../examples/managed/Workbench.Checks/Program.cs)。为一个新的行为先写验收描述，例如“不进入重解析点目录”。再判断它需要纯规则、真实文件系统还是 Windows 专项测试。

对任务控制器做纸面推演：上一轮进度晚到，新一轮已运行，界面应忽略什么？记录状态与 `runId`，不要靠随意延时解决。

## 检查理解

**把所有事件搬到 ViewModel，业务逻辑就分离了吗？** 没有。如果它仍直接操作控件、调用所有系统 API 并拥有不清晰的状态，只是换了代码位置。真正的分离体现在输入输出、归属和独立验证能力。

**为什么不能把文件访问失败当成空结果？** 因为调用方无法区分“没有文件”和“未能读取”。这会污染统计、历史和用户判断。失败必须有不同于合法结果的表达。
