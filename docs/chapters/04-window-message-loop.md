# 04 窗口为什么会“未响应”

分析器本身能运行，但把它放进按钮事件后，窗口拖不动，取消按钮也按不下去。CPU 可能很高，也可能只是被某次同步 I/O 挡住。共同点是：负责界面事件的执行路径没有及时回到分发循环。

本章解释输入到事件处理的关系，并找出耗时工作应该在哪里离开界面路径。

## 窗口与消息

在传统 Win32 编程中，`HWND` 标识窗口。输入、绘制、尺寸变化等事件通过消息机制进入处理过程。拥有窗口的线程需要继续处理消息，用户才会看见更新并得到响应。

下面是缩减的 Win32 教学片段，不是完整窗口工程：

```cpp
MSG message{};
BOOL result;
while ((result = GetMessageW(&message, nullptr, 0, 0)) > 0) {
    TranslateMessage(&message);
    DispatchMessageW(&message);
}
// result == 0 表示收到退出消息；-1 表示获取消息失败。
```

循环取出消息，分派到相应窗口过程。事件处理函数执行太久，下一条消息就可能等待。并非所有消息都简单排队：同步发送消息可能直接进入接收方处理，引入等待甚至重入。

因此“处理到一半再调用一个函数处理消息”不是可靠的通用修复。嵌套消息循环可能让第二次点击、关闭和其他事件在对象尚未恢复一致性时执行。

## 框架包装了机制，没有消除执行约束

WPF 的 Dispatcher 负责调度界面线程上的工作，许多界面对象要求通过所属线程访问。Qt 的事件循环和对象线程归属也有明确约束。Electron 则需要区分主进程、渲染进程及其事件循环，不能直接套用一张 WPF 线程图。

WPF 教学片段可以直接对比两种情况：

```csharp
// 反例：点击处理期间阻塞 UI 线程。
Thread.Sleep(3000);

// 对比练习：让等待期间能回到调度循环。
await Task.Delay(3000);
```

这不是说把同步函数加上 `async` 就会自动后台执行。调用 `Task.Delay` 提供了可等待的非阻塞等待；一个直接执行大量计算的 `async` 方法，在遇到真正挂起点前仍可能占住调用线程。

目录扫描使用的某些文件系统调用是同步的。第 06 章会用任务调度把这段工作移走，同时保留进度和取消契约。

## 两种“等”会互相锁住

假设界面线程用 `.Result` 等后台任务结束，后台任务完成前又要回到界面线程更新状态。前者不再处理调度工作，后者等不到执行机会，就可能形成互等。

通常应让界面事件一路 `await` 到结果，避免同步阻塞 UI。工作线程也不应持有应用锁，再同步要求 UI 完成某项工作。先释放锁或传递独立消息，才能减少锁顺序与界面调度交织的风险。

窗口关闭同样是事件。隐藏窗口不等于销毁窗口，窗口销毁不一定代表整个进程结束；托盘、其他窗口、后台任务和框架退出策略都可能影响生命周期。

## 检查理解

**加上 `async` 关键字就不会卡界面吗？** 不会。关键在于耗时工作是否阻塞当前执行路径，以及等待是否真正让出执行机会。CPU 工作和同步 I/O 仍需安排到合适位置。

**为什么不循环调用“处理待办消息”来保持响应？** 因为这会让原本以为不能交错的事件进入同一段逻辑，制造重入、重复启动或关闭过程中访问对象的问题。应设计明确的任务与状态边界。
