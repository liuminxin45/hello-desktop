# 14 SQL 与 SQLite：历史记录怎样可靠落盘

工作台需要在重开后展示分析历史。把记录追加到 JSON 数组很快能做出来，但筛选、并发和迁移逐渐困难。SQLite 提供本地关系数据库能力；它仍需要你定义事务和恢复语义。

## 先让模型对应用户问题

一轮任务有稳定身份、开始时间、状态与结果。教学模型可以先只保存终态：

```sql
CREATE TABLE runs (
    id TEXT PRIMARY KEY,
    started_utc TEXT NOT NULL,
    status TEXT NOT NULL CHECK (status IN ('Succeeded','Failed','Cancelled')),
    file_count INTEGER,
    total_bytes INTEGER
);
CREATE INDEX runs_by_started ON runs(started_utc DESC);
```

UTC 时间使用一致的格式，展示时再按用户时区转换。错误或取消时允许结果为空，避免让零同时代表未完成与合法统计。

SQL 把“要什么数据”与内部访问方式分开。查询最近十条记录时使用 `ORDER BY ... LIMIT 10`；索引可以减少查找工作，也增加写入和空间成本。用实际查询计划判断，不给每个字段机械加索引。

插入用参数绑定，不把路径或错误文本拼进 SQL。参数处理值，表名、排序字段等结构选择仍需要受控白名单。

## 事务定义一个一起成立的变化

假设要同时写任务终态和多条统计项。没有事务时，进程可能只保存一半。显式事务把它们组织为提交或回滚的单位：

```sql
BEGIN IMMEDIATE;
-- 插入本轮记录与相关统计；遇到失败由调用方执行 ROLLBACK。
COMMIT;
```

`BEGIN IMMEDIATE` 提前尝试取得写事务，可能遇到忙或锁冲突。SQLite 支持并发读，但同一时刻的写事务仍需要协调。短事务、合理 busy 策略和明确的单写入队列，比让 UI 无限等待更容易解释。

事务只覆盖数据库。它不能自动与文件导出、远端请求形成一个跨系统原子操作。若数据库写了成功而文件尚未落盘，需要定义中间状态和恢复步骤。

## WAL 改变记录方式，不会消灭所有锁

WAL 把提交变化追加到日志，checkpoint 再推进主数据库文件。它可以改善某些读写并发，但仍有单写入者、checkpoint 和长读事务等条件。

运行中的最新提交可能还在 `-wal` 文件里。不能假定复制一个 `.db` 文件就得到完整备份。优先使用适用的在线备份机制；离线复制也必须明确所有连接、日志和一致性条件。随手删除 `-wal` 不是空间维护方案。

WAL 的共享内存协调还要求合适的存储环境，不能把它当作任意网络共享上的通用多用户数据库。具体可靠性也取决于 SQLite 版本、同步设置和底层存储条件。

## schema 升级也会失败

保存 schema 版本，启动时识别支持的范围。在迁移事务中修改结构和版本，失败就回滚并保留诊断信息。是否能回退旧应用，取决于旧应用能否理解迁移后的数据，不由 EXE 能否替换决定。

重开后看到之前的 Running 记录，不能直接宣告成功：原任务可能已中断。若未来要持久化运行中状态，应增加启动身份和恢复策略。本章终态模型暂不承诺断点续算。

## 动手：实际验证回滚和并发

运行 `node examples/sqlite/transactions.mjs`。这个独立 SQL 实验使用 Node 内置 SQLite 绑定，验证参数化写入、回滚、第二连接写冲突和失败迁移；它不是 .NET 数据层实现，也不模拟真实断电。

阅读输出中的 SQLite 版本，保存自己的结果。再推演：事务外先导出文件、事务内保存历史，哪一步失败会留下什么？写出能在重启后识别的状态，而不是声称跨系统事务已经成立。

## 检查理解

**开启 WAL 后为什么仍会 busy？** WAL 没有把写事务变成无限并行。写入者竞争、checkpoint 或其他状态仍可能需要等待，必须有受控超时与失败处理。

**程序包回滚，数据库是否自动回滚？** 不会。数据可能已迁移。发布前要定义备份、恢复、前向修复或支持的降级条件。
