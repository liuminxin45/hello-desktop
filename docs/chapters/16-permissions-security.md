# 16 标准用户、UAC 和安全边界

工作台在开发者管理员账号下一切正常，交给标准用户却不能写配置。把 EXE 设置成“总是以管理员运行”似乎解决了问题，却让文件解析、插件和界面都获得了更大的能力。

本章先确定哪些操作真正需要权限，再设计可信输入到系统能力的边界。

## 进程带着身份执行

Windows 使用访问令牌等信息描述进程的身份、组与权限。访问文件、注册表和其他受保护对象时，系统根据访问控制等条件做判断。UAC 提权改变执行上下文，并不让程序逻辑自动正确。

“当前用户属于管理员组”和“这个进程正在提升上下文中运行”也不是同一判断。诊断权限失败时，需要记录实际进程上下文、目标对象和请求操作。

本案例的大多数操作只需要访问用户选择且允许读取的目录，配置与历史写入用户位置。先修正错误的数据位置，再考虑机器级操作是否需要单独提升。

## 缩小高权限能力

| 操作 | 常见设计方向 |
| --- | --- |
| 分析用户目录 | 普通用户进程，拒绝不可访问内容或按约定失败 |
| 保存用户设置 | 用户数据目录或用户范围键 |
| 安装机器级组件 | 安装过程按需提升 |
| 修改受保护全机设置 | 小而明确的受控操作，验证输入与调用方 |

若确实需要高权限辅助进程，不能把“运行任意命令”“写任意路径”作为通用 IPC 入口。接口应只表达必要动作，校验参数、调用方和目标；普通 UI 不必因此整体提权。

独立进程只是故障边界之一，只有配套身份与权限设计，才能讨论安全隔离。

## 输入跨边界时要重新判断

文件选择器返回的路径后来可能变化。拖放、命令行、网络响应、插件和 IPC 请求都可能带来不可信内容。检查类型、范围、大小与路径归属，并考虑检查后到使用前的变化。

不要把外部参数拼进 shell 字符串再执行。优先使用不经 shell 的明确程序路径与参数列表，限制可执行动作。原生库也从受控位置加载；顶层绝对路径还需要配套依赖搜索策略。

Electron 的 preload 应提供窄接口，例如“请求扫描已选目录”，而不是把整个 IPC 或 Node 能力交给 renderer。隔离上下文、禁用不必要的 Node 集成和校验 IPC 来源需要共同考虑；一个配置开关不能替代整个权限设计。

## 凭据与诊断材料

不要把密钥写进仓库、客户端常量或普通日志。客户端分发给用户的内容通常不能被视为不可提取的服务器秘密。用户凭据按实际场景选择系统保护机制，并考虑退出、撤销与多人登录。

日志和 dump 可能包含路径、文档、内存中的令牌与用户数据。支持包需要最小化、明确收集范围、访问权限和保留周期；脱敏不能靠把扩展名改掉。

代码签名帮助建立发布者身份和完整性关系，不证明业务无漏洞，也不保证操作系统永不提示风险。签名凭据应在受控交付环节使用，不能进入公开教程仓库。

再用标准用户完整走一遍设计。遇到写入失败，先定位目标与 ACL，说明为什么这个操作确实需要机器级能力，或把它移到正确的用户位置。

本章是设计与检查练习，不会自动改变机器的 UAC、ACL、全局 DLL 搜索或安全设置。

## 检查理解

**为什么“插件在单独进程”不足以叫沙箱？** 地址空间隔离减少部分崩溃影响，但相同权限下仍可能访问同一批文件和系统能力。安全隔离需要额外约束。

**把密钥藏在原生 DLL 而不是 JavaScript，就安全了吗？** 不会由语言决定。发布到用户机器的固定秘密可能被分析或在运行时观察，应重新设计身份与授权方式。
