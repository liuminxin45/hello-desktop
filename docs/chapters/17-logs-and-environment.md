# 17 客户说“打不开”：从环境与日志开始调查

“打不开”可以指双击后没有进程、进程马上退出、后台存活但没有窗口，也可能只是窗口出现在另一块显示器。先给现象分类，再选工具，往往比立刻重装依赖有效。

本章建立一条从用户描述到可证伪假设的调查路径。

## 先把“什么时候、哪个版本”对齐

记录产品版本与构建标识、启动方式、发生时间和时区、操作系统架构、进程是否出现，以及最后一个正常行为。安装包版本、EXE 文件版本和 SDK 版本可能不同，不能只抄一个关于窗口里的数字。

一条结构化教学日志可以包含：

```json
{
  "utc": "2026-10-28T09:00:00Z",
  "event": "ScanFailed",
  "build": "teaching-build",
  "runId": "sample-run-1",
  "stage": "Enumerate",
  "errorCategory": "AccessDenied"
}
```

这是格式示意，不是一次实际故障输出。它让不同组件可以按任务关联，避免只留下“error”与一段无法定位的文本。完整路径、文档内容和凭据不是默认必要字段。

时间戳帮助排序，不保证不同机器时钟完全一致。单次操作耗时宜用适合的单调计时方式；日志异步写入也可能影响最终落盘顺序。

## 根据问题选择证据

| 现象 | 先看什么 | 要排除的误判 |
| --- | --- | --- |
| 进程没有出现或极快结束 | 启动命令、安装路径、事件日志、短时间跟踪 | “没看到”不等于从未创建 |
| 加载原生模块失败 | 架构、错误码、导入与实际搜索路径 | 顶层 DLL 在就应能加载 |
| 进程仍在但无窗口 | 线程、托盘、窗口位置、启动状态日志 | 一定是崩溃 |
| 只有特定用户失败 | 用户位置、权限、代理与配置来源 | 一定要管理员运行 |
| 只在升级后失败 | 旧配置、数据库、残留模块与新依赖 | 新 EXE 自身一定有错 |

事件查看器适合查系统已有的相关事件，不保证每个失败都有完整业务原因。Process Explorer 帮助观察进程、线程、模块和句柄；Process Monitor 用于按进程与时间过滤文件、注册表等访问；Dependencies 用于理解静态依赖。

每个工具回答的问题不同。不要先开全部工具长期采集，再试图从大量无关事件里找解释。

## 一条因果链怎样成立

假设“缺间接 DLL 导致打不开”。先确认失败发生在加载阶段，再找到被请求模块与实际路径，核对架构和依赖。用受控补齐正确产物的方式验证启动是否改变，而不是随意下载同名 DLL。

如果启动恢复，只能支持这条条件下的原因。还需检查为什么安装包漏带依赖，避免把根因停在“客户机器缺文件”。可能是打包清单、条件构建或旧版本残留暴露问题，不能没有证据就归咎用户环境。

调查报告至少写：现象、环境、证据、假设、验证、结论、剩余不确定性。反证也要保留，例如“模块实际已成功加载，因此缺 DLL 假设不成立”。

## 支持包要小、明确、可解释

支持包可以包含版本清单、经筛选的日志、配置结构摘要和用户明确提供的故障材料。设置大小与保留限制，让用户知道收集什么。dump 作为单独材料处理，因为内存可能远比普通日志敏感。

日志本身也会失败：磁盘满、权限变化、进程突然结束。不要让记录一条日志阻塞关键 UI，也不要承诺最后一条事件一定已经持久化。

## 动手：写一份“打不开”调查

选择一个自建故障：无效目录、配置损坏或模块路径错误。先不修改系统配置，收集足以区分阶段的证据，再提出一个能通过实验否定的假设。

托管 CLI 可以用于无效输入练习：从仓库根目录运行扫描命令并给出不存在的目录，检查进程退出码和错误表达。不要把这个小实验称为完整客户支持包验证。

## 检查理解

**Process Monitor 里出现 `NAME NOT FOUND`，就找到根因了吗？** 没有。程序可能正在进行正常的候选路径搜索。必须看后续是否成功、最终错误和具体阶段。

**为什么每轮任务需要自己的标识？** 多任务、异步组件和重试的日志会交错。只有时间与线程号不足以稳定还原同一业务执行，任务身份提供跨组件关联。
