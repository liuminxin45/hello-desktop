# 13 配置该放文件还是注册表

工作台需要记住上次选择的目录。最方便的实现是把配置写在 EXE 旁边，开发目录中一切正常；安装进受保护位置后，标准用户却不能保存。数据位置和权限现在成了产品行为的一部分。

## 先分清数据属于谁

| 内容 | 归属与位置思路 | 卸载时的默认考虑 |
| --- | --- | --- |
| EXE、DLL、静态资源 | 安装目录，由安装过程管理 | 随产品移除 |
| 用户设置与历史 | 对应用户的应用数据目录 | 明确保留或由用户选择清理 |
| 全机设置 | 机器级受控位置或注册表 | 需要权限与多人使用约定 |
| 缓存、临时文件 | 可重建、可限额的目录 | 按明确归属清理 |
| 日志与 dump | 单独限额与保留周期 | 不混入正常配置或公开提交 |

在 .NET 中使用已知文件夹 API，而不是把用户名拼入 `C:\Users\...`：

```csharp
string root = Path.Combine(
    Environment.GetFolderPath(Environment.SpecialFolder.LocalApplicationData),
    "HelloDesktop", "Workbench");
Directory.CreateDirectory(root);
```

这只说明获取位置的方法，不自动保证写入成功。目录权限、磁盘空间、文件占用和路径变化仍可能导致失败。

## 文件与注册表分别适合什么

配置文件适合结构化内容、导出、比对和迁移；注册表适合某些 Windows 配置与系统集成。`HKCU` 主要表达当前用户范围，`HKLM` 表达机器范围并通常涉及更高写入权限。不要因为用了注册表，就把所有操作提升为管理员。

64 位 Windows 对部分注册表位置提供 32 位与 64 位视图。两个不同位数的组件可能实际看到不同内容，因此诊断要记录进程架构与访问视图。并非所有键都重定向，不能靠猜测固定追加 `Wow6432Node`；使用明确的视图选择 API 和官方规则。

配置还需要优先级。例如内建默认值 → 用户设置 → 本次命令行覆盖。机器策略若有强制语义，需要单独定义，不任由任意用户文件覆盖。记录最终值来自哪里，支持调查会简单很多。

## 写配置不是覆盖字符串那么简单

直接截断原文件再写入，进程中断可能留下半个 JSON。常见方案是在同一目录写临时文件，完整写入并按需要刷新，然后用适用的替换操作提交。

但“原子替换可见性”和“断电后保证持久化”不是同一承诺。替换 API、文件系统、存储和刷新方式都影响保证；不要仅用重命名就宣称绝对不丢数据。失败时保留可恢复版本，并让用户知道哪些设置没有保存。

配置应有格式版本。迁移先读取旧内容，再生成新内容，验证后提交；不要在解析失败时悄悄覆盖旧文件，破坏调查材料。

## 文件路径也有边界

中文、空格、长路径和相对路径都可能暴露错误。对路径使用适当的 Unicode API；字符串长度、路径长度和缓冲区字节数分别处理。

重解析点可以把目录访问引向另一位置。为了避免循环和意外扫描范围，本书扫描器默认跳过重解析点，并声明统计不是快照。这个策略降低复杂度，不构成防御恶意目录变更的完整安全边界：检查属性之后，目标仍可能变化。

遇到第二个实例同时保存配置，要选择单实例、进程间互斥或有明确合并规则的存储。不管采用哪一种，都不能用“最后写入者通常没问题”代替决定。

## 动手：三种环境检查

用标准用户保存配置；输入含中文和空格的路径；让配置文件损坏后重开。记录位置、错误、恢复方式和是否保留原数据。

再推演两个进程同时更新不同设置。若都执行“读全量—改一项—写全量”，第二次写可能覆盖第一次改动。设计序列化访问或版本检查，解释冲突怎样报告。

不要在本章练习中修改全局系统键；使用自己的应用键与独立练习目录。仓库不会为写教程自动更改你的注册表。

## 检查理解

**为什么配置不默认放 EXE 旁边？** 安装文件和用户数据有不同权限、升级与卸载周期。开发目录可写，不能证明安装目录适合持久数据。

**注册表读不到值，是否一定是值不存在？** 还可能是用户范围、进程位数、视图或权限不同。先确认访问上下文，再判断数据是否缺失。
