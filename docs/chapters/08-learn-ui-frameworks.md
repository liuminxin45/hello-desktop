# 08 怎样学会一套 UI 框架，并迁移到另一套

工作台已经有任务、取消和错误表达。现在团队有人提出改用 Qt，另一位希望用 Electron 复用 Web 经验。如果只比较“按钮怎么写”，会忽略真正影响维护的条件。

本章以同一任务建立学习方法。目标不是给框架排总榜，而是判断当前产品需要承担哪些成本。

## 先学语言，再抓运行关系

C# 不是 WPF 的同义词，C++ 也不等于 Qt。语言决定表达方式和部分内存模型；框架组织窗口、事件、对象与平台能力；打包方案还决定部署。

学习新框架先运行官方最小样例，在入口、按钮事件、后台完成和退出位置设断点。回答：哪个线程或进程执行？状态归谁？对象何时结束？发布后需要什么？这些问题能迅速连接已有经验。

## 三条常见路线

**WPF：**先读懂 Application/Window 与 XAML 的关系，再做布局、绑定和命令。接着学习 Dispatcher、异步和资源生命周期，最后接入原生 API 与发布。绑定没有生效时，检查数据上下文、属性通知和诊断信息，不盲目重建整个窗口。

**Qt：**先选 Widgets 或 Quick/QML。Widgets 路线从对象归属、信号槽、布局到 Model/View；Quick 路线另学声明式属性、绑定与 C++ 边界。随后集中解决 QObject 线程归属、排队连接和销毁时机。`QThread` 对象所在线程与其管理的执行线程不是同一概念，不能仅凭函数写在子类里就推断回调位置。

**Electron：**先理解 main、renderer、preload 与 IPC，再引入 React/Vue 等 UI 库。后台任务放在哪里、谁能访问文件、renderer 能请求什么，需要在学习 CSS 之前有清楚边界。长时间同步工作也会阻塞主进程；“用了多进程框架”不代表所有业务天然隔离。

每条路线都要尽早做一次分发，在干净环境运行。开发模式成功只能验证部分条件。

## 其他 Windows 路线怎样进入

WinUI 与 Windows App SDK 需要理解 XAML、调度、Windows 能力、包身份及运行时部署。WinUI、MSIX 和 Windows App SDK 不是同一个概念；选择 UI 不自动替你决定打包。

WinForms 适合从事件驱动和现有业务界面学习，但仍要补状态分离、跨线程操作和 DPI。维护 MFC 时，先建立 Win32 消息、资源、消息映射、文档/视图与编译链接的对应关系，再考虑迁移。旧框架不意味着所有既有工程都应该重写。

进一步的官方入口和分路线任务见[框架学习指南](../frameworks.md)。

## 用同一需求做小迁移

只迁移“开始扫描、显示状态、允许取消”这一条路径。分析器契约保持不变，分别记录：

| 观察项 | 应留下的证据 |
| --- | --- |
| 调度 | 点击、工作和完成回调的位置 |
| 状态 | 同一时刻哪个组件允许修改任务状态 |
| 原生边界 | DLL 通过何种适配接入，在哪个进程 |
| 交互 | 键盘、DPI、错误反馈的检查结果 |
| 交付 | 运行时、依赖、打包与诊断方式 |

迁移不是把 C# 语法逐句翻成 C++ 或 TypeScript。保留的是行为不变量，实现机制应采用目标框架可靠的惯例。

## 选择依据应能被反驳

“团队熟悉 TypeScript，需要跨平台，原生接入较少”可以成为 Electron 的候选理由；但要验证启动、资源和分发条件。需要深度原生 SDK 接入且团队熟悉 C++，可以先验证 Qt；仍不能跳过部署与对象生命周期。

写出限制条件，再记录小实验。如果结论依赖某版本或某机器，就注明。没有相同条件的实验，不给性能、内存或生产效率编造数字。

## 检查理解

**已经会 WPF，换 Qt 最值得先学什么？** 先学对象归属、事件循环、信号槽和线程约束，再把已有状态模型映射过去。控件 API 可以边做边查，生命周期误判更可能造成工程问题。

**为什么不把所有框架各做一个完整工作台？** 首轮会重复大量相同业务，延长反馈周期。先交付一条路线，再用最小迁移暴露机制差异，更容易判断需要补什么。

第二阶段到这里形成可响应、可验证的交互路径。下一章让分析能力离开原工程，讨论 DLL 与构建产物。
