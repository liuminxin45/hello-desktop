# 06 后台任务：异步、取消、超时和关闭

开始命令已有统一入口。现在要保证“按下取消”之后，状态、资源和结果不会互相矛盾。取消不是一个控件效果，而是一段需要所有参与者遵守的协议。

## 先给任务一个身份

为每次执行分配 `runId`，并记录 `Idle → Running → Cancelling → Cancelled`，或 `Running → Succeeded / Failed`。终态由实际执行结果决定。

收到取消请求时，任务可能已经完成，只是完成消息尚未显示。这种情况下可以呈现成功；不要因为用户按过取消，就把已经提交的成功结果改写为取消。语义需要统一并写进测试。

晚到的进度也可能属于上一轮任务。更新界面前，先检查 `runId` 是否仍是当前轮，并确保状态还允许接收进度。单纯把进度条清零不能解决串轮问题。

## 把工作放到合适的位置

可等待的网络或文件 API 可以通过真正的异步等待释放当前执行位置。CPU 密集工作以及本案例使用的同步目录遍历，可在桌面进程里安排到工作线程；这并没有让底层同步调用变成可中断调用。

下面是控制器中的教学片段，省略状态通知和关闭处理：

```csharp
using var source = new CancellationTokenSource();
try
{
    var result = await Task.Run(
        () => scanner.Scan(directory, source.Token), source.Token);
    // 接受结果前确认仍属于当前 runId。
}
catch (OperationCanceledException) when (source.IsCancellationRequested)
{
    // 本轮取消；其他失败单独表达。
}
```

`Task.Run` 的 token 可以让尚未执行的任务被取消，但任务开始后，扫描器仍要主动检查 token。异步 API 的 token 也需要实现支持，不能假定传进去就能停止任何系统操作。

取消检查点放在取得新条目、进入下一目录和提交结果前等安全位置。若底层文件系统调用长期不返回，取消延迟可能超过预期；需要测量、限制范围或隔离工作进程，而不是承诺严格毫秒级取消。

## 进度也是负载

每处理一个文件都切回 UI，十万个文件就会制造十万次更新。界面真正需要的是可理解的最新状态，可以按时间或批次节流。结束时再发送最终状态，不能因为节流丢掉终态。

`Progress<T>` 在创建时捕获的同步上下文会影响回调位置。WPF 中常在 UI 线程创建它，但扫描器仍不应直接依赖控件。Qt 和 Electron 要分别落实排队连接或 IPC，不照抄这个 .NET 机制。

## 超时、取消和失败分别处理

超时是调用方规定的等待预算；取消是停止意图；失败是执行遇到错误。超时后，远端任务或底层工作可能仍继续执行。因此不能立刻启动一个重复操作，尤其是在会写数据或提交订单的流程中。

重试应以故障类型和幂等性为前提。权限不足不是通过重复十次就能修复的临时错误。进度状态里也应保留“失败”与“取消”的区别，方便第 17 章关联证据。

## 关闭时谁等谁

关闭流程先停止新任务，再请求取消，异步等待任务收尾，最后释放信号源和界面资源。不要在 UI 线程同步等待，同时要求后台任务回到 UI 完成收尾。

如果设定收尾预算，到期后允许退出，就需要说明未完成写入、日志刷新和子进程的处理。强制结束进程不是协作取消的等价实现；对不可信模块，第 12 章再讨论隔离与强制终止的边界。

## 动手：验证四条路径

运行[托管检查](../../examples/README.md)，确认正常、预取消、路径失败和资源释放。再在自己的 UI 练习中验证：连续开始、开始后取消、取消后立即重开、运行中关闭。

记录每一轮身份、请求时间、最后进度和最终状态。当前仓库的托管检查并不覆盖真实窗口关闭或调度竞态，不能据此宣称 UI 生命周期已经通过验证。

## 检查理解

**收到取消请求后还返回成功，一定是 bug 吗？** 不一定。完成可能已先发生。需要定义成功提交点和取消接受点，再判断时序是否违反契约。

**为什么只给 `Task.Run` 传 token 还不够？** 它无法强行安全停止已经执行的任意代码。工作函数必须检查取消，并在退出前按约定释放资源和处理未完成结果。
