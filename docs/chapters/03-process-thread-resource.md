# 03 进程、线程、内存和句柄：程序到底占着什么

现在程序可以运行了。连续分析几百次后，它越来越慢。任务管理器显示内存增加，但这还不能说明哪段代码泄漏。先弄清程序究竟持有什么资源。

本章从一个文件流出发，建立“谁拥有、何时结束”的思考方式。

## 执行单位与资源容器

进程提供地址空间、已加载模块和系统资源的环境。线程是在其中执行指令的路径，同一进程的线程可以访问进程内的共享内存，因此也可能产生竞争。

虚拟地址不是物理内存的直接编号。两个进程中相同数值的地址不代表同一份对象；把指针值通过管道传给另一个进程，并不能让对方使用这个对象。共享内存要通过系统建立映射，并设计跨进程的数据布局与同步。

栈保存调用过程中的数据与控制信息，堆支持更灵活的分配周期。不要把“值类型都在栈、引用类型都在堆”当成通用定位规则；对象布局、捕获和运行时实现会改变具体位置。调查时应观察实际对象和分配路径。

## 内存之外还有句柄

打开文件后，程序持有的是对某个系统对象的引用。Windows 用句柄表达许多这样的引用。文件已经不再使用，但句柄没关闭，可能阻止其他操作，也消耗系统资源。

```csharp
// 教学片段：异常离开作用域时，同样会执行释放。
using var stream = File.OpenRead(path);
long length = stream.Length;
```

这里 `stream` 是托管对象，同时持有原生资源。垃圾回收主要管理托管内存；不能靠“等 GC”安排文件解锁时间。`Dispose`、`using` 或合适的 `SafeHandle` 让释放发生在可解释的时刻。

C++ 的 RAII 用对象析构落实类似的归属：拥有资源的对象退出作用域时释放。拷贝、移动与共享所有权要另行设计；把一个裸句柄复制两份，不等于获得两个可以各自关闭的独立资源。

## 给案例做一张归属表

| 资源 | 拥有者 | 借用者 | 结束条件 |
| --- | --- | --- | --- |
| 目录枚举器 | 本次分析调用 | 迭代代码 | 完成、取消或异常 |
| 文件流 | 读取该文件的调用 | 分析函数 | 本文件处理结束 |
| 取消信号源 | 任务控制器 | 分析器持有 token | 本次任务收尾完成 |
| 原生库模块 | 原生适配器 | 导出函数调用 | 所有调用与回调结束后 |

“借用”意味着不能自行释放，也不能保证在拥有者结束后继续使用。异步操作尤其容易跨越原本想象的作用域：启动任务后立刻释放资源，而任务尚未读取它，就会造成晚到的访问。

## 看见增长之后怎样判断

先固定输入与次数，区分工作集、私有提交、托管堆、句柄数和线程数。工作集变化还受操作系统驻留策略影响；缓存和运行时初始化也可能让前几轮增长。

有意义的泄漏假设应更具体：“每次分析后，仍有一个文件流被列表引用”“每次订阅事件后没有解除，旧窗口仍能被引用”。用对象引用链或句柄调查验证，再修复并重复相同负载。

只写“加一次 GC 后内存下降”不能证明正确释放了资源。它可能掩盖生命周期设计，也不能保证客户机器在需要时发生回收。

## 动手：验证异常路径也释放资源

运行托管检查程序。它包含扫描后文件可独占打开的检查，以及预取消、正常完成和输入失败等场景。阅读实现，找出每个资源的作用域。

然后做推演：如果把流放进全局列表，哪些操作会延长其寿命？如果在读取中抛异常，`using` 后的结果赋值没执行，流是否仍释放？最后在自己的小程序中重复打开和关闭，记录句柄数趋势，而不直接下泄漏结论。

验收材料是归属表和一次异常路径说明。实际性能与长期泄漏实验仍需独立执行，短小检查不代表耐久性验证。

## 检查理解

**对象已经不可见，资源一定释放了吗？** 不一定。可见性与引用可达性不同，其他对象、事件订阅或任务仍可能持有它；即使已不可达，最终释放时间也未必符合业务要求。

**为什么不能在任务开始后立刻释放取消信号源？** 控制器还可能需要发出取消，任务也可能使用相关注册。拥有者应把信号源的生命周期覆盖到任务收尾结束，而不是只覆盖启动调用。
