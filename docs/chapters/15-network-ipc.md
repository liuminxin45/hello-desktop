# 15 网络与 IPC：消息发出去之后呢

分析器移到工作进程后，函数调用变成消息。宿主发出开始请求，等待超时。它能判断工作没开始、正在执行、已经成功但响应丢失中的哪一种吗？只凭超时通常不能。

## 把每条消息放进协议

即使都在本机，协议也需要身份、版本和边界。一个教学请求可以是：

```json
{
  "version": 1,
  "requestId": "run-2026-001",
  "operation": "StartScan",
  "directory": "C:\\TeachingData"
}
```

响应应区分 `Accepted`、进度和终态，不能把“收到请求”当作“完成工作”。`requestId` 用于关联请求、去重、查询和日志；它不天然就是安全凭据。

TCP 和字节模式管道提供的是字节流，不保证一次读取恰好得到一条完整消息。需要长度前缀或其他明确分帧，并限制消息大小。消息模式管道也要正确处理分段读取和缓冲区条件。序列化前后验证协议版本、字段和范围。

## 选传输，先看需求

HTTP 适合请求/响应与既有服务；长连接适合持续通知；命名管道可承担 Windows 本地 IPC；共享内存适合大量数据，但控制协议和同步仍不可缺少。

本地不等于可信。同一机器上的其他进程也可能尝试连接，管道需要访问控制和调用方策略。远程 HTTPS 需要正常证书验证，不以关闭 TLS 校验修复代理或证书配置问题。

代理、DNS、连接、TLS、HTTP 状态、协议解析和业务错误属于不同层。调查时保留层次信息，不把所有情况简化成“网络不通”。

## 重试为什么会重复执行

宿主发请求后，工作进程已经保存结果，但响应丢失。直接换一个 ID 重试，可能创建第二份结果。更稳妥的方案是让同一业务请求使用稳定幂等键，接收者保存或查询其状态，重复请求返回同一执行关系。

幂等也有范围：保存多久、重启后是否保留、相同 ID 不同参数怎样拒绝，都必须写进契约。只有内存中的去重表，不能承诺进程重启后仍不重复。

“至少一次发送 + 去重”往往比模糊承诺“绝对只执行一次”更可实现。跨数据库、文件和外部系统时，要逐个说明提交与恢复边界。

## 取消、重连与背压

取消消息必须指向已识别的任务，并能查询是否已经结束。连接断开只说明传输关系中断；是否停止工作要由协议决定。重连后先查询状态，再决定恢复展示、重新请求还是报告未知。

进度产生得比消费快，会积压内存。可合并进度、限制队列长度和并发任务，终态则需要可靠保存或查询。不能为了“不卡主线程”把消息无限塞到后台队列。

超时预算应覆盖明确阶段：连接、握手、接受、执行或停止。等待结束后释放相关资源，并记下任务处于哪种已知或未知状态。

## 动手：画出三种超时

为“请求未送达”“执行已开始但未完成”“执行已完成但响应丢失”各画一条时序。只给宿主一个 timeout 异常，让它写出下一步能安全做什么。

再补上稳定请求 ID 与状态查询，观察哪种不确定性能消除，哪种仍依赖接收方持久化。若实现练习服务，应只监听受控本机地址，不把教学端点直接暴露为生产服务。

验收是一份消息格式、状态转换、去重期限和失败恢复表。本仓库未实现完整 IPC 产品协议，这些行为需要读者根据所选传输验证。

## 检查理解

**重连成功说明任务恢复了吗？** 不说明。它只恢复通信能力，业务状态还需要识别、查询与协调。

**为什么在消息里加 `requestId` 仍不等于幂等？** 因为接收方还要定义如何识别重复、保存结果和处理相同 ID 的不同输入。字段本身没有执行这些规则。
