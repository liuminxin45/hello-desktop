# 24 AI 时代怎样负责一次工程改动

写完一轮工作台之后，AI 也许能很快生成另一个窗口、原生接口包装和流水线。代码生成变快，并不会替你决定取消语义、兼容范围和失败恢复。高级工程能力仍然体现在这些判断及其证据上。

本章用“修复取消无效”收束全书，并区分使用 AI 开发与开发 AI 产品。

## 先定义可被检查的任务

不只要求“帮我优化扫描”。给出已有契约：同一时刻一轮任务；取消后不接受旧进度；遇到读取失败不返回零冒充成功；UI 不同步等待工作结束；不改变 SDK ABI。

再提供最小相关代码、复现步骤、实际错误和环境。没有必要交出整个用户目录、凭据或完整 dump。上下文越多不一定越好，关键是足以理解边界且来源清楚。

可以让 AI 先列假设和验证方式。例如取消无效可能是只取消了等待、工作不检查 token，或底层调用尚未返回。这些解释需要不同证据。

## 审查一段看似合理的建议

假设候选修改只有：

```csharp
return Task.Run(() => Scan(directory), cancellationToken);
```

它把工作安排到线程池，也把 token 交给调度。但若任务已经开始，`Scan` 不观察 token，就不能靠这段代码安全停止扫描。正确方向是把协作取消传入工作逻辑，并在受支持检查点观察，而不是事后把任意结果标成 Cancelled。

还需检查异常释放、进度串轮、关闭流程，以及取消后是否可能留下半份历史。一个局部“修好了”的改动可能只是把故障移到退出时发生。

这是教学候选代码，不是某次模型实测输出。判断来自机制与可运行检查，不来自模拟一段 AI 对话。

## 以风险组织验证

| 改动 | 优先验证 |
| --- | --- |
| UI 异步与状态 | 重复启动、晚到回调、取消与关闭交错 |
| 原生包装 | 位宽、编码、长度、所有权、导出与版本 |
| 数据迁移 | 中断、回滚、旧格式和重试 |
| 安装更新 | 干净环境、占用、失败恢复、权限 |
| CI 与发布 | 最早失败、实际产物、符号映射、权限边界 |

测试可以由 AI 协助起草，但预期不能只重复实现。例如实现把所有错误转成零，测试也断言零，两者一致仍然违反产品契约。预期应来自需求、不变量和独立可推算的输入。

保留“建议—接受/拒绝理由—实际验证”的简短记录，尤其是重要接口与发布变更。人工编写的代码也承担同样责任。

## 工作方式会变，基础机制仍决定判断

AI 可以减少样板代码、帮助定位陌生入口、提出诊断假设和解释工具结果。工程师更需要把问题拆得可验证，识别不同层次的错误，判断何时已经有足够证据。

把 AI 生成速度直接等同生产效率，忽略了审查、失败重试、集成与维护成本。衡量改进时，应看真实需求完成与质量结果，不虚构统一提升倍数。

学习顺序也可以改变：先借助 AI 完成一个小闭环，再集中补调度、生命周期、ABI 和交付机制。但每个关键边界最终应能由维护者独立解释。

## 如果产品本身接入 AI

那是额外的产品路线：模型调用延迟、流式结果、取消、成本、离线策略、凭据、内容到工具执行的授权，都需要设计。模型给出的文字与程序实际执行必须有明确边界。

不要因为 UI 已有聊天框，就把任意系统命令交给模型。第 12、15、16 章的进程、协议和权限原则继续适用。检索、记忆或提示词更新，也不等于训练模型权重。

## 综合验收

选择[毕业项目](../capstone.md)中的一个需求变化，交付：设计取舍、实现与检查结果、SDK 兼容性材料、安装升级计划和一份故障调查。AI 可参与，但你应能不依赖它的措辞解释每项关键决策。

本书提供的是学习与判断路径，不以完成阅读授予职级。将这套方法用于新的业务、陌生 SDK 和实际用户环境，才是下一轮成长。

## 检查理解

**AI 和测试都说通过，为什么还需要审查？** 它们可能共享同一错误假设，遗漏系统和生命周期边界。需要独立的需求约束、实际执行证据和风险判断。

**初学者是否应该完全不用 AI？** 不必。可以用它解释与协助实现，同时要求自己能画出运行关系、预测错误并验证结果。避免把无法解释的生成物当作已掌握能力。
