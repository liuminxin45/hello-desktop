# 19 卡顿、死锁、泄漏和慢启动如何区分

程序没有退出，却在扫描时卡住。有人提议加线程，有人认为是内存不足。先看系统究竟在计算、等待还是不断分配，比凭现象选修复更可靠。

## 把“慢”改写为可测量问题

定义时间范围、输入规模、构建配置和指标。例如从点击开始到首个有效反馈、总扫描耗时、取消请求到终态、冷启动到可操作。不要把首次初始化和缓存命中的后续运行直接混为平均值。

记录机器、输入、负载与重复次数，比较相同条件。小样本可以帮助发现方向，不能直接支持所有客户环境的性能承诺。

## 先分类，再选工具

| 观察 | 候选解释 | 下一步证据 |
| --- | --- | --- |
| CPU 高，界面慢 | 大量计算、忙等、事件风暴 | CPU 采样与调用热点 |
| CPU 低，界面不动 | I/O、锁、同步等待或外部服务 | 线程栈、等待关系与访问时间线 |
| 内存持续增长 | 缓存、积压、对象引用或原生分配 | 堆/分配、队列长度与释放路径 |
| 句柄持续增加 | 文件、事件、线程等未释放 | 句柄类型、创建与关闭关系 |
| 启动慢 | 模块加载、配置、扫描、同步网络 | 启动阶段日志和追踪 |

这些是候选解释，不是由单一指标推出的根因。低 CPU 不证明死锁，高工作集不证明泄漏。

## 卡死需要等待关系

UI 线程等工作线程，工作线程又同步等 UI，就是第 04 章的典型互等。还可能是锁 A 与锁 B 顺序相反，或一个外部调用一直不返回。

抓取同一进程多个时刻的线程栈，有助于区分一直停留和缓慢推进。再记录锁拥有者、等待目标与可打破条件。只看到一个线程在等待，不足以证明形成闭环。

修复应消除具体依赖，例如避免持锁调用外部代码、统一锁顺序、让 UI 异步等待；不要简单给所有等待加短超时，再把状态错误留给下游。

## 从采样走向时间线

CPU 采样回答时间主要花在哪些执行路径；ETW 等追踪能关联事件、调度、I/O 和阶段。WPR 用于采集，WPA 用于分析；选合适配置，限定目标和时间。

以下是手动教学命令，需要相应工具与权限，只在自己的实验环境执行。先确认没有其他正在进行的采集：

```powershell
wpr -status
wpr -start GeneralProfile -filemode
# 只复现一次目标操作，然后停止自己启动的采集。
wpr -stop .cache/analysis.etl
```

不要终止其他人的追踪来运行练习。分析时把点击、初始化、加载、分析、保存等阶段标记到同一时间线上。工具开销、丢失事件和配置范围也要记录。

## 泄漏与积压的处理不同

内存保留可能来自事件订阅，让旧窗口仍可达；也可能来自生产速度超过消费速度，待处理进度无限排队。前者检查引用链和解除订阅，后者需要限流、合并与背压。

原生分配不会因为托管 GC 自动识别而全部回收。句柄、内存映射、驱动缓冲区等还需要各自的观察方法。不要用强制 GC 作为所有资源问题的通用修复。

## 动手：把三个故障分开

在独立练习中分别制造界面短时阻塞、两把锁的互等、保留文件流。先写预测，再观察 CPU、线程栈和句柄。故障只作用于可丢弃的教学进程。

报告必须包含基线、证据、具体机制、修复和同条件对照。仓库中的短小资源检查只验证确定性释放的局部行为，不替代长时间泄漏或性能测试。

## 检查理解

**加更多线程为什么可能更慢？** 竞争、切换、I/O 饱和和 UI 回调积压都可能增加。需要确定瓶颈与并发上限，不能把线程数当吞吐量。

**为什么要在修复后重复相同输入？** 否则性能变化可能来自缓存、负载或数据变化。对照条件是支持修复结论的基础。
