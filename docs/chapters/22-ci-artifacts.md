# 22 CI：从源码到可追溯的安装包

多人协作后，手动构建会出现“忘了带 DLL”“符号找不到”“这个包到底是哪次改动”的问题。CI 把重复步骤放进受控执行环境，同时留下源码与产物的对应关系。

本章先区分验证流水线与产品发布，再讨论如何沿同一条链条推进。

## 一条流水线应该回答什么

输入是源码提交、工具链与依赖；输出是检查结果及可识别产物。每个阶段失败就停止依赖它的阶段，不让打包成功掩盖早先失败。

```mermaid
flowchart LR
    S[源码提交] --> C[目录与内容检查]
    C --> B[构建与契约检查]
    B --> P[整理产物与符号]
    P --> I[安装升级演练]
    I --> R[受控发布]
```

图中的产品安装和发布是目标流程；本教程仓库当前实现前面适用于独立实验的验证与归档，不代表完成了成品安装器、签名或自动更新。

## 仓库自带的 CI 做什么

实际工作流见[课程与实验检查](../../.github/workflows/verify.yml)。它检查章节结构和本地链接，运行 SQLite 事务实验，在 Windows runner 构建托管与原生实验，再用托管调用方验证原生边界，并归档实验产物。

这些任务不需要模型 API、签名证书或用户凭据。工作流只有仓库读取所需权限。源码变更触发检查，不配置定时内容生成。

在本地可分别运行：

```powershell
npm test
dotnet run --project examples/managed/Workbench.Checks -c Release
cmake -S examples/native -B .cache/native -A x64
cmake --build .cache/native --config Release
ctest --test-dir .cache/native -C Release --output-on-failure
```

原生构建需要适当的 Windows C/C++ 工具链；这些条件见实验说明。`npm test` 验证的是课程与 SQL 实验，不会自动证明 .NET、原生或安装场景通过。

## 缓存不应该成为隐藏依赖

固定 SDK 范围与目标架构，依赖恢复依据公开配置或锁定策略。缓存可以提速，但缓存不存在时也应成功；缓存键需要反映相关依赖变化。

不要把开发机上某个绝对目录作为 runner 的前提。需要内部包时，清楚分离公开构建与内部条件，避免把凭据写进仓库或构建日志。

Windows GUI 测试还涉及交互会话、桌面、权限和工具限制。无人值守 runner 上编译 WPF 成功，不代表真实焦点、DPI 或 UAC 流程已经验收。

## 版本、二进制、符号和源码一起归档

每个可交付版本至少留下构建标识、源码提交、工具链、依赖清单、产物校验与符号映射。哈希帮助检查文件是否一致，不单独证明来源可信；公开分发还需要相应信任链。

签名一般位于验证后、发布前的受控环节，只有必要权限可以访问证书或签名服务。来自外部分支的内容不应自动取得发布权限。GitHub Actions 与 Jenkins 的语法不同，但权限、阶段和产物责任可按同一原则设计。

## 别把“绿灯”解释得过宽

一次工作流成功只说明该工作流的任务与环境通过。没有执行安装、网络故障或兼容旧调用方，就不能把成功描述为“全部验证”。

失败时先找最早的实际失败，再看后续清理或报告错误。报告阶段空值异常可能只是前面没有生成产物的后果，不能替代真正的构建诊断。

## 动手：从制品反查源码

选一次实际运行，下载或检查产物元数据，找到对应提交、二进制和符号。再在全新目录构建，记录哪些条件来自仓库，哪些来自 runner 镜像。

本地检查、远端工作流与最终安装验收分别记录在[验证记录](../../editorial/validation.md)。没有运行结果之前，只称“工作流已配置”。

## 检查理解

**为什么测试后要归档当时的 PDB，而不是故障时重编？** 因为故障分析需要精确匹配实际二进制，重编可能改变符号身份和代码布局。

**所有检查都绿了，能立刻声称产品可交付吗？** 只能依据检查范围判断。签名、安装、升级和用户环境等门槛若未执行，仍不能扩大结论。
