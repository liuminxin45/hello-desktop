# 20 看不到源码时：二进制检查与逆向辅助维护

一个旧 DLL 只有二进制和几页文档。新系统中它加载失败，或者某个参数导致错误。源码缺失不代表完全无法调查，但也不意味着反编译器能还原作者的全部设计。

本章使用自己编译的小模块，练习从可直接验证的信息逐步接近行为。

## 先看文件，再看反汇编

先保存文件哈希、来源和版本。检查 PE 架构、导入、导出和调试信息。某个错误也许只是位数不匹配或缺依赖，不需要立刻阅读汇编。

导出表回答外部能按什么名字找到入口；导入表展示部分静态依赖；字符串提供路径、消息和协议线索，但未必在当前执行路径使用。压缩、运行时加载和优化都可能改变可见信息。

先写事实：“文件是 x64 PE，导出包含 `wb_sum_bytes`”。再写假设：“可能对输入求和”。不要把名字或字符串直接当成执行结果。

## 静态与动态观察互补

IDA、Ghidra 可帮助分析控制流和数据引用；x64dbg 等动态调试器可以观察实际寄存器、内存与执行。托管程序集则常有不同的元数据和分析工具，不能把它与纯原生机器码混为一种材料。

编译器会优化、内联和重排。反编译器显示的变量名、类型和伪代码是分析结果，不是原始源码。必要时回到调用约定、指令和具体输入核对。

Windows x64 常见原生调用约定使用寄存器传递前几个整型或指针参数，栈上还有相应规则。学习时结合官方 ABI 文档，不能把这套规则照搬到 x86 或其他架构。

## 用已知模块做可校准练习

本书字节求和函数接收缓冲区、长度和输出地址。先保留源码，再在暂时不看源码的情况下观察 Release 产物：

1. 找到导出及其引用，定位实现。
2. 识别空指针与零长度等检查候选路径。
3. 预测输入 `{1, 2, 255}` 和空输入的返回与输出。
4. 用本书调用方实际执行，再对照源码。

优化后不一定保留你预想的循环结构。没有看到逐字节循环，并不证明不存在等价求和。练习目标是把预测和事实对齐，而不是截图圈出几个熟悉指令。

## 给结论分层

| 层次 | 示例 |
| --- | --- |
| 直接观察 | 导出名存在；该输入返回成功和 258 |
| 有证据的推断 | 某分支很可能检查参数有效性 |
| 尚待核实 | 所有长度、并发调用和异常输入都安全 |

有限输入只能证明相应执行。第三方库导入了某网络 API，不代表它必然上传数据；看到一个安全检查，也不代表所有路径都经过它。动态未执行的路径与静态被优化的结构，需要不同证据。

对无源码模块建立兼容包装时，仍应依赖已确认契约，不根据伪代码随意猜结构体布局。无法确认所有权或线程约束时，记录风险，考虑进程隔离和受限调用。

## 学到哪里就够用

桌面工程主线要求能查架构、导入导出、符号、基本调用与行为，不要求每个人掌握漏洞利用、驱动逆向和所有汇编。需要深入时，再系统学习指令集、ABI、链接装载和调试。

练习以自编模块或允许分析的材料为对象，关注维护、互操作和诊断。不要从一个教学模块推导商业软件的授权或使用规则。

## 检查理解

**反编译器把参数显示为 `int`，能直接据此写调用声明吗？** 不能。类型可能是推断，必须结合位宽、调用方、实际访问和公开契约确认。

**既然有源码，为什么还用它练逆向？** 因为可以校准工具和自己的判断，区分编译优化、工具推断与真实行为。直接面对未知大程序更难发现误解。

诊断阶段完成后，还要把这些能力带进安装和发布，避免每次只修好开发机器。
