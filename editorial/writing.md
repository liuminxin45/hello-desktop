# 写作与事实核对约定

## 读者与目标

读者已有一门语言基础，希望独立设计、交付和维护 Windows 桌面客户端。避免一方面假定读者会排查 ABI，另一方面反复讲解变量和循环。

路径与正文状态以 `content/chapters.json` 为准，`docs/index.md` 由它和正文标题生成。`docs/curriculum.md` 保留课程范围与设计，不维护第二套完成状态。只为实际完成的正文创建章节入口；规划不能伪装为完整教程。

## 一章怎样成立

从贯穿案例已经完成的能力出发，引入一个新需求或故障。讲清它为什么需要新机制，说明职责、状态、线程/进程、资源归属、失败行为和至少一种相关替代方案的代价。

每章给出学习成果和验收方法；至少有一个故障或条件变化需要读者推演。示例应能独立回答本章问题，不预先引入全部后续模块。

不要按 API 名称堆目录，不把控件清单当教程。术语首次出现时用具体问题解释。C# 是语言，WPF 是 UI 技术，Windows 是系统平台，各层职责分别表达。

## 事实、版本与证据

优先使用 Microsoft Learn、框架官方文档、工具官方仓库及自建可复现实验。正文可以提供相关官方链接，不强制读者跳转后才能理解本章。

重点官方核对材料放在 `content/verification.json`，实际运行范围放在 `editorial/validation.md`。没有执行示例、核对目标条件前，不填写“已验证”。每个实验记录 Windows/架构、工具链、框架、构建配置、依赖版本、步骤、结果及限制。

区分官方机制、自建实验、教学示意和推测。构建成功不等于兼容性验证；能读调用栈不等于确认根因；框架默认配置和行为随版本变化时，需针对实际版本核对。

性能、资源占用、包体积和开发效率没有对照实验时不排名。反编译结果与工具报告不能单独证明完整运行行为。dump、日志和支持包仅保留必要且脱敏的教学材料。

## 示例与图解

主案例为“桌面任务工作台”，以 C# / .NET / WPF 解释 UI，原生 C ABI 实验用 C11 实现并提供 C/C++ 头文件。当前附带独立实验，不将其称为完整工作台。其他框架按相同任务演示差异，不机械复制全部章节。

图解优先回答职责、时序、生命周期和边界问题。Windows 消息循环、WPF Dispatcher、Qt 对象线程归属和 Electron 多进程模型不得强行合成一张相同的实现图。

教学故障用自编可控材料，明确预期结果和恢复方法；不把故障注入写成真实客户事故，不编造运行输出、截图和故障统计。

## 后续扩展边界

- 首版固定 24 章主线；完整 WPF 实现及其他框架成品需要独立运行与验收。
- 不把独立实验验证的 Windows x64/.NET 10 组合扩大成全部框架和架构支持。
- 逆向主线聚焦维护与诊断，不自动扩成汇编、漏洞利用或驱动专题。
- 正文和代码的许可证、站点技术和发布方式另行确定；当前不复制其他仓库的许可证或发布完成态。

## 提交前检查

运行 `npm test` 和 `npm run check:links`；涉及实验时运行相应托管、原生或 SQL 检查。重新生成目录使用 `npm run docs:index`。当前没有站点构建，不声称已通过网站、移动端或公共部署验收。
